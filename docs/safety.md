# Safety

DeltaForge does not run learner commands through a shell. Test and benchmark commands are executed as argument vectors.

Fixtures are copied to temporary directories before execution. State, config, reports, and benchmark history use atomic writes. DeltaForge avoids destructive filesystem operations outside known temp or project paths.

Learner output is drained concurrently and capped in captured diagnostics. Timeouts terminate the learner process group where the platform supports it. Pack, stage, template, fixture, and file-expectation paths are restricted to safe relative paths.

Projects pin the selected pack version, source directory, and content digest. A completed stage also records the pack and learner-tree digests that passed; changing either requires a fresh complete test run before `next` or `commit`.

Projects on state schema 1 do not load in 1.0; recreate them. Frozen decision 11 permits the break, and the renumbered FlashIndex stage IDs would invalidate their progress maps regardless.

## The browser boundary

The workbench service can execute pack-defined build and run commands, so its browser boundary is security-sensitive. It binds only to the loopback interface on an ephemeral port, requires a 256-bit token generated by the operating system CSPRNG on every request, compares it without token-dependent early exit, validates the `Host` header against its own address, and rejects any request whose `Origin` is not exactly its own. Mutating requests additionally require that `Origin` header and an `application/json` content type, so an unrelated page in the same browser cannot induce one. Request headers and bodies are bounded. No endpoint executes an arbitrary command, and none serves a file from the repository.

The token is sent to the background child over a private stdin pipe, not its command line. Its discovery record lives in the per-user DeltaForge home and is written mode `0600` inside a mode `0700` directory on Unix; Windows inherits the user's profile ACL. The service rejects an empty token. `deltaforge exit` uses the same authenticated mutation boundary to stop the service cleanly.

The token necessarily travels in the query string for the request that loads the page itself (there is no page script yet to attach a header) and for the `EventSource` connection the page keeps open for live updates (the browser's `EventSource` API cannot set custom headers at all). Every other request the page makes — every read and every mutation — sends the token in an `X-DeltaForge-Token` header instead, checked the same way as the query string. Immediately after loading, the page also removes the token from its own URL with `history.replaceState`, so it does not sit in the address bar or get written into browser history on that load or any later in-app navigation. `DELTAFORGE_NO_BROWSER=1` still prints the full URL, token included, to stdout, since the whole point of that mode is a human copying it into a browser by hand.

Run leases and event-journal updates use OS file locks. A corrupt journal is moved aside as `workbench-events.corrupt-<timestamp>.json` and rebuilt, so it cannot brick the workbench; only the few most recent such files are kept, so repeated corruption cannot accumulate copies without limit. Benchmark history is capped the same way, oldest records first.

Accepting a connection costs a thread and a socket before the peer has proved anything, so the number of connections that may sit in that unauthenticated window at once is bounded, and a connection over the bound is closed without being served. A connection stops counting against it the moment it presents a valid token, because `/api/v1/events` is a long-lived stream that legitimately holds its thread for as long as the tab is open — bounding only the unauthenticated window means an unauthenticated peer cannot crowd out the learner's own browser.

Browser requests name projects by opaque registry identifier and never carry a filesystem path — with one exception. Creating a project necessarily lets the learner choose where their code goes. That endpoint accepts a parent directory and a leaf name, never a full path, and one guarded function decides whether the pair is acceptable: the leaf must be a single restricted component, the parent must already exist and canonicalize inside the learner's home directory (or, when `DELTAFORGE_WORKSPACE` is set, inside that directory instead), no component below that root may be hidden, the parent must not be inside an existing DeltaForge project, and the target must not exist. Each refusal has a test. The reasoning is recorded as an amendment in [product/architecture.md](product/architecture.md).

`deltaforge init` keeps its freedom to write anywhere the shell can reach. It is invoked by a person at a prompt or by CI, not by a web page.

## Build processes can outlive DeltaForge

A build or test command runs in its own process group, so cancelling or timing out a run can terminate the whole tree rather than just the immediate child. The cost of that isolation is that a signal aimed at DeltaForge does not reach the child: if DeltaForge itself is killed outright — `kill -9`, a crash, Ctrl-C at a prompt — an in-flight `cargo build` is reparented to init and runs to completion on its own.

This is a known limitation, and it is bounded rather than dangerous. Recorded state stays correct: the run lease is released and the next run marks the interrupted job as such. The orphan runs only until the build it was already doing finishes — seconds for the bundled packs — and it cannot corrupt the build directory, because Cargo takes its own lock on `target/` and a later DeltaForge run simply waits for it. What is left is transient CPU use by a build nobody is waiting for any more.

Killing the orphan with the parent needs a different mechanism on each platform — `PR_SET_PDEATHSIG` on Linux, a job object on Windows, and neither exists on macOS or the BSDs — and the obvious portable substitute, recording the child's process id and killing it on the next run, is unsafe: process ids are recycled, so it can name a process that is no longer the build. None of that is worth the risk for a bounded, self-clearing symptom, so DeltaForge does not currently attempt it.
